# 正文测量栈的按需分配

## 本次卡死反馈

用户报告应用整体卡死后，先对正在运行的安装版采样，没有直接改动窗口事件代码。采样时应用已经重新启动，第一次采样包含正常的 SwiftUI 更新与事件等待；第二次采样主线程几乎都在等待事件，没有捕获持续死锁。随后用户确认暂时恢复，要求继续检查布局。因此本轮没有将「暂时恢复」归因于任何修复，先保留这两份采样供本机复查：

- `/tmp/timeline-app-hang-20261028.sample.txt`
- `/tmp/timeline-app-hang-second.sample.txt`

## 确认的重复工作

正文的富文本与各宽度高度已经全局缓存，但 `InteractiveTaskText` 仍在初始化时创建另一套独立的 `NSTextStorage` / `NSLayoutManager` / `NSTextContainer`，`makeNSView` 随后再向其中设置空内容。滚回已有缓存的条目时，这套对象不参加测量也会被分配。

现在先查共享高度缓存，仅在未命中时创建测量栈。宽度变化或者正文替换后仍用同一个测量器重新测量；缓存失效和正文的实际布局方式保持原有规则。这轮不调整时间轴的间距、正文宽度、行高或编辑器高度协议。

新增回归先在原实现中出现三项失败：缓存重建行仍有测量栈，变窄前就已分配测量器，100 个缓存命中的正文对象创建了 100 套测量栈。修改后均通过；真实 SwiftUI 宿主中重建长 Markdown 行的高度、正文及链接仍一致，变窄与替换正文也正确重新测量。

Debug 局部构造检查中，100 个缓存命中的正文对象从分配 100 套额外测量栈变为 0 套，构造耗时从约 2.82 ms 到 2.24 ms。修改后 Release 相关回归中约 2.16 ms，完整回归中则约 3.20 ms，可见计时本身也有波动。这个测试不包含整页挂载、布局或窗口呈现，不能把约 0.58 ms 的局部差异解读成明显的滚动加速；它也说明仅这一处重复分配不足以解释原有长帧。

## 整页对照

与前一轮使用同一份冻结日记副本、相同合成场景与 Release 配置，以 4500 pt/s 驱动滚动，刷新预算约 8.33 ms。基准期间没有并行编译、功能回归或其他性能探针。修改前与最终版本各运行一次完整滚动场景，均 8 项通过。

下表是移动帧主线程同步工作的 p95（毫秒），首次 / 再次分别指第一次向上浏览及返回后再次向上浏览。

| 场景 | 修改前，首次 / 再次 | 修改后，首次 / 再次 |
| --- | --- | --- |
| 日记数据副本（57 条） | 7.38 / 5.92 | 6.84 / 5.46 |
| 合成日记 30 条 | 1.03 / 1.30 | 0.81 / 0.85 |
| 合成日记 90 条 | 7.43 / 7.17 | 8.11 / 8.00 |
| 任务笔记 90 条 | 7.38 / 7.15 | 8.08 / 7.82 |
| 原生文本对照 | 3.02 / 2.50 | 2.24 / 1.52 |

再次浏览的距离保持一致：数据副本 2700 pt、30 条日记 5522 pt、90 条日记 17822 pt、90 条笔记 18264 pt，没有通过缩短页面改变测试路程。首次遍历受懒加载高度修正影响，日记副本约 2967 / 2971 pt，90 条任务笔记约 24510 / 24701 pt。

90 条日记超预算帧由首次 21/512、再次 12/464 变为首次 22/503、再次 15/460；90 条笔记由首次 12/479、再次 10/476 变为首次 19/475、再次 16/470。数据副本首次由 3/65 变为 1/70，再次仍各 1 帧。原生对照也明显变快，结合长页面略慢的结果，本轮不能声称整体跟手改善，保留范围是缓存命中时不再创建闲置测量对象。

后续应先增加行创建、宽度提案、测量命中率与各阶段耗时的计数，定位长页面在跨条目时的布局峰值；当前数字不足以支持继续增加同类缓存或扩大预加载。

## 后续方向

长页面的同步滚动开销仍主要落在 SwiftUI / AppKit 的布局阶段。下一步需要统计跨条目时的行创建数、正文宽度提案、测高命中率，再决定减少重复提案还是减少行挂载工作。已有高度缓存命中的正文不应继续堆叠同类缓存；扩大预加载也需同时控制打开成本。

所有自动化窗口继续走 Headless，测试与基准串行执行，并用窗口服务器监控检查是否有可见测试窗口。整页性能仍沿用显示回调驱动的隐藏窗口探针；它测的是主线程同步工作，不是最终呈现 FPS 或触控板到像素延迟。
