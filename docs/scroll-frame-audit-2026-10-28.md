# macOS 日记与长笔记连续滚动测量（2026-10-28）

本轮增加测试和测量报告，应用的渲染与编辑实现不变。目的是确认长日记快速滚动时，主线程是否能跟上刷新节奏，而不是根据平均耗时决定是否迁移 WebKit。

## 测量方法

- Apple M2 Pro，内置 Retina 屏幕；CoreVideo 返回的标称刷新周期为 8.33 ms（120 Hz）。使用 release 优化编译。
- `CVDisplayLink` 在独立线程提供刷新节奏，每次只允许一个主线程回调待执行，避免主线程变慢后测试输入无限堆积。
- 每次主线程回调按实际经过时间推进滚动位置，速度 4,500 pt/s，分别记录滚动位置更新、布局、绘制调用耗时，以及回调间隔和排队延迟。
- 分别向上首次遍历、向下返回、再次向上遍历。每次最多 8 秒，到边界后停止；验证实际移动帧数和距离，防止把没有滚动的空跑误报为流畅。
- 同时记录刷新线程实际回调间隔，以及主线程回调尚未完成、不得不合并的刷新次数，区分刷新源波动与主线程跟不上。
- 窗口为 1,424 × 876，字体缩放 1.1，附加行距 0。使用 `QuietWindow` 和 `Headless`，不激活测试应用；窗口服务器监测同步运行。
- 场景包含简单原生文本对照、30 条混合长短日志、90 条混合长短日志、90 条任务笔记，以及当前日记数据的临时副本。合成数据每三条有一条多段 Markdown，包含列表、链接、代码块和引用。
- 数据副本仅复制 `journal.json`，不复制附件。报告只包含时序、位置和汇总数据，不包含日志正文。

## 指标边界

这是隐藏窗口下的主线程滚动、布局和绘制调用基准，不是屏幕最终呈现帧率测试。

直接推进原生 clip view 的滚动位置，随后显式执行所需布局和绘制；不向系统注入鼠标事件，也不模拟完整触控板手势与惯性。显式布局使测量可重复，但与系统实际采用异步滚动和合成时的工作分布可能不同。

`missedOpportunities` 根据主线程回调间隔与标称刷新周期估算错过的刷新机会；`coalescedTicks` 直接统计主线程回调待处理期间被合并的刷新回调。两者都不能当作 WindowServer 实际丢弃或重复呈现的帧数。隐藏窗口也不能充分覆盖 GPU 合成、真实输入到显示延迟、图片解码，以及编辑器已激活时的滚动。

“首次遍历”指当前窗口中第一次向上遍历，不代表整个进程、字体或 Markdown 缓存完全冷启动。懒加载列表在首次遍历中可能修正内容总高度，因此首次与再次遍历的距离可能不同。

性能测试不为共享机器上的时序设置脆弱的硬性通过线；通过表示测量完成且确实滚动了内容。是否满足帧预算需要查看输出指标。统计计算另有确定性的单元测试。

## 第一轮 release 结果

| 场景 | 首次向上工作 p95 | 再次向上工作 p95 | 首次向上主线程最大间隔 | 首次向上合并刷新次数 / 刷新回调数 |
| --- | ---: | ---: | ---: | ---: |
| 简单原生文本对照 | 3.14 ms | 2.42 ms | 17.35 ms | 2 / 666 |
| 30 条日志 | 0.86 ms | 0.83 ms | 21.90 ms | 1 / 180 |
| 90 条日志 | 12.88 ms | 7.78 ms | 33.35 ms | 47 / 570 |
| 90 条任务笔记 | 4.76 ms | 4.98 ms | 16.74 ms | 10 / 600 |
| 当前日记副本 | 50.88 ms | 22.86 ms | 59.38 ms | 79 / 115 |

当前日记副本首次遍历的移动帧工作中位数为 22.92 ms，31 个移动帧中 29 个超过 8.33 ms；再次遍历中位数为 15.42 ms，46 个移动帧中 41 个超预算。首次遍历布局累计 752.3 ms，滚动位置更新累计 2.6 ms，绘制调用累计 0.4 ms。这里绘制调用的低耗时不能解释为 GPU 绘制免费，因为窗口隐藏且合成可能异步执行。

当前日记副本的刷新线程间隔 p95 为 8.63 ms，最大 9.01 ms；主线程却出现 59.38 ms 间隔，说明该轮主要问题不能用刷新源不稳定解释。

## 第二轮 release 复测

重新启动测试进程，使用相同构建和参数，未同时运行采样或编译。

| 场景 | 首次向上工作 p95 | 再次向上工作 p95 | 首次向上主线程最大间隔 | 首次向上合并刷新次数 / 刷新回调数 |
| --- | ---: | ---: | ---: | ---: |
| 简单原生文本对照 | 3.24 ms | 2.50 ms | 13.15 ms | 1 / 662 |
| 30 条日志 | 22.01 ms | 21.39 ms | 30.15 ms | 64 / 181 |
| 90 条日志 | 14.37 ms | 12.93 ms | 25.62 ms | 67 / 567 |
| 90 条任务笔记 | 7.46 ms | 6.58 ms | 17.29 ms | 20 / 609 |
| 当前日记副本 | 16.95 ms | 9.35 ms | 37.48 ms | 23 / 117 |

当前日记副本首次遍历中位数为 3.16 ms，89 个移动帧中 13 个超过 8.33 ms；再次遍历中位数为 1.91 ms，100 个移动帧中 6 个超预算。首次遍历布局累计 395.3 ms，仍远高于滚动位置更新和绘制调用。

两轮日记结果波动明显，30 条日志也出现布局长尾。因此不能把第一轮单个 p95 当作稳定性能承诺，也不能仅凭条目数量或懒加载阈值解释所有停顿。简单原生文本对照的工作 p95 两轮接近，说明至少不能把全部差异归因于测试调度本身。

## 判断

结果支持“仍有主线程布局超预算”的判断，不能据此断言 SwiftUI 必须被替换，或整体 WebKit 一定更快。日记页面的长尾开销和运行间波动更值得关注；重复遍历也并非都能消除超预算。

调试版本的独立采样也观察到 SwiftUI 布局和原生文字排版调用。后续优先检查滚动期间新条目出现、长文本测量与布局重复工作，再用同一基准验证小范围修改。当前数据不足以把某个具体布局函数认定为唯一原因。

两轮 release 各运行 8 项测试，均零失败且没有跳过性能场景；窗口守门测试通过，窗口服务器监测没有记录到可见测试窗口。测试通过不表示达到流畅度目标。

另运行 15 项相关回归，零失败，其中 2 项耗时性能场景按默认条件跳过；这两项已在上述 release 测量中显式运行。

## 重跑

先在独立终端启动窗口监测：

```sh
swiftc -O scripts/test-window-monitor.swift -o /tmp/timeline-window-monitor
/tmp/timeline-window-monitor 600 > /tmp/timeline-frame-window-monitor.log
```

运行合成场景及可选的本机数据副本场景：

```sh
TIMELINE_FRAME_PROBE=1 \
TIMELINE_SCROLL_PROBE_DATA="$HOME/Library/Application Support/Timeline" \
TIMELINE_FRAME_PROBE_OUTPUT=/tmp/timeline-frame-results \
swift test -c release --filter 'AAAWindowWatchTests|ScrollFramePerformanceTests|ZZNoVisibleWindowsTests'
```

不传 `TIMELINE_SCROLL_PROBE_DATA` 则跳过个人数据副本场景。不传 `TIMELINE_FRAME_PROBE=1` 时，只运行确定性统计测试和窗口守门测试。每一遍的汇总与逐帧数据写到输出目录中的 JSON；基准应与编译、采样或其他高负载测试分开执行。
