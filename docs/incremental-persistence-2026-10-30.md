# 本地增量持久化方案与同步修复

## 结论与边界

建议在 TimelineCore 中使用本机 SQLite，开启 WAL，以单写队列提交事务；保留现有云端不可变字段增量、检查点、回执与原图文件协议。SQLite 文件、WAL 和 SHM 不能放进共享 iCloud 文件夹。原图仍按内容摘要存独立文件，不降分辨率、不转码，不放进数据库 BLOB。

本轮实施同步可靠性及附件生命周期修复，没有替换本地存储引擎。正文目前仍是 journal.json，字段基线仍是 state.json；新增提交标识和上一版基线是迁移前的恢复措施。它减少错误确认及重启回滚风险，但仍有全量编码和额外的恢复文件写入，不能声称已经实现本地增量持久化。

## 当前证据

在修复前的 macOS Debug 测试中，10,000 条日志初次云端写入 5,459,312 字节，修改一条后云端仅写 459 字节；但本地同步基线约 5,460,049 字节、journal 约 3,378,942 字节仍整份重写。前台保存约 43.9 ms，同步整轮约 797 ms。这是单次诊断样本，不是 iOS Release 性能承诺，也不是修复后测量。

因此继续压缩图片无法解决文本库每次全量扫描、编码和写盘的问题。本轮的双文件恢复也会增加发生记录变化时的本地写入量，SQLite 的价值既是降低开销，也是替代跨文件提交协议。

## 本轮修复

- 正文和同步基线带同一 commit ID。先保存上一版已提交基线和新基线，再确认正文写入；确认成功之后才发布批次或回执。重启仅加载与正文 commit ID 一致的基线；不一致时回退上一版，不能匹配则以新设备身份重建检查点。同步导入不再先触发一次无确认的正文保存。
- transport 缓存同时绑定设备 ID、规范化同步目录和 commit ID；更换目录重置传输状态并发布全量检查点，自己的最后一个云端批次丢失时重新发布检查点。目录路径只是当前本机隔离键，下一版应使用云端库 UUID。
- 同 owner 的独立 Board 确定共同主 ID，保留不同正文。旧 ID 留作归档别名，收藏去重、打开中的编辑器写入和历史查询都解析至主 ID。已合并原文的摘要避免用户整理正文后旧内容反复复活；原文仍可从历史恢复。
- 新增图片引用重新核对云端对象；历史上传缓存不能阻止重传被清理的原图。iCloud 占位文件不当成对象丢失。空闲轮询不扫描整座图库；每日维护及重新打开应用时重新核验引用。
- 双端附件导入属于原草稿，同一草稿按选择顺序串行导入，限制大原图并行内存；提交前检查 pending；关闭继续导入，丢弃递增草稿代次以忽略迟到结果。部分失败保留成功结果并显示错误。iOS 导入完成回写原入口草稿，重复打开复用导入中的会话。

这不是磁盘硬件故障或断电的严格 durability 保证：当前使用 Foundation 原子替换，没有跨文件 fsync 协议。后续 SQLite 事务需要按所选同步等级和实际崩溃测试验收。

## 方案选择

| 方案 | 适配情况 | 主要代价 |
| --- | --- | --- |
| SQLite + GRDB | 推荐。双端共用 TimelineCore，事务、迁移、查询及 observation 现成；兼容目标需锁定并验证合适版本 | 新依赖及版本管理；仍需自己设计同步事务 |
| 系统 sqlite3 + 小型 Swift 封装 | 备选。平台自带，可精确控制 SQL 和事务 | 绑定参数、语句生命周期、迁移、忙等待和观察机制都要维护 |
| Core Data | 能实现事务持久化，也能支持现有最低系统 | 为当前 Codable 模型引入对象上下文和映射成本，现有自定义字段同步仍需维护 |
| SwiftData | 暂不采用 | 当前最低 macOS 13，而 SwiftData 要 macOS 14；还要迁移现有字段同步 |
| 每条记录一个 JSON | 不推荐作为最终存储 | 小文件数量增长，正文、游标、outbox 仍缺乏一次提交的事务；索引及备份维护复杂 |

先做小型双端 GRDB 兼容性验证，再锁定依赖；若项目决定保持依赖规模，则使用系统 sqlite3。不要同时长期维护 JSON 和数据库两份权威数据。

## 建议数据边界

第一阶段不要求把每个 Swift 属性拆成 SQL 列。按实体保存 Codable payload，先消除全库重写，再按查询需要增加索引列。

| 表 | 主键与用途 |
| --- | --- |
| metadata | schemaVersion、libraryID、deviceID、generation、revision、nextTaskNumber |
| tasks | taskID；payload 及 day、dueAt、startAt、completed、sortPosition 查询列 |
| logs | logID；payload 及 day、createdAt、taskID 查询列 |
| summaries / tags / boards | 各自稳定 ID、payload；Board ownerKey 唯一逻辑映射另表保存 |
| board_aliases / board_history | aliasID → canonicalID，旧原文及历史版本；保留恢复入口 |
| preferences / local_drafts | 收藏顺序、固定关联；本机草稿单独标记不同步，不能混进云端记录 |
| sync_fields | (recordKey, fieldName)；值、逻辑时钟、设备 ID；删除标记明确保留 |
| sync_peers | (libraryID, generation, peerID)；已接收 sequence 与必要的回执状态 |
| sync_outbox | (deviceID, generation, sequence)；不可变批次字节/摘要、状态、重试信息 |
| image_refs / image_objects | ownerID → 原图摘要；本地存在、云端确认、待传、保留期限、保护来源 |

任务、日志、Board 的一次本地修改在一个事务中更新实体、对应字段时间戳、图片引用和 outbox。导入远端批次在一个事务中应用字段/别名/编号修正、更新接收位置，并生成必要的本机合并增量。事务提交后才能发布已接收回执。DB 已提交但云端发送失败时重放同一 outbox 字节，不重新分配序号。

原图先写临时文件并校验摘要，再原子移动至内容寻址目录，最后事务插入引用。中途失败留下的无引用对象经过保留期回收；数据库不先指向尚未完成的原图。pending 导入只在本机草稿中保留，成功日志事务提交后才清空草稿。

## 性能与线程

- 单写队列在后台提交小事务，输入缓冲继续防抖；主线程只发送实体修改命令和接收最小变更集合。
- JournalStore 的全库 days 字典先作为兼容读投影，后续按页/日期查询。仅改存储而继续每次构造全量 SyncContent.records/applying，CPU 开销仍会随库大小增长，必须逐步替换为 dirty entity/field 索引。
- outbox 只处理发生变更的记录；游标和回执更新不能触发正文全库重写。大批次导入分块准备，事务内避免图片解码和网络等待。
- 搜索索引、NotebookIndex、标签派生数据按变更 ID 更新；回调只使相关视图失效，不能整页跟随打字和拖动重算。
- WAL checkpoint 设预算，在空闲/后台做；备份用 SQLite backup API 或一致性快照，禁止运行中只拷贝主数据库文件。
- 原图保护引用要来自当前正文、草稿、历史、最近删除和备份；长期离线设备的租约/回收期限仍需沿用保守策略。不能仅根据当前正文引用清理图片。

## 双端迁移步骤

1. 保留原始 journal、state、transport 和恢复基线的只读迁移备份，记录摘要和模型版本；暂停同步写入，正常排空后台 journal writer。
2. 先按本轮 commit ID 规则选定一致基线，识别合法未同步本机修改。导入实体、字段时间戳、删除标记、别名及图片保护引用；不要把整库重盖成本机最新修改。
3. 在临时数据库事务中导入；校验记录数、逐实体规范化摘要、收藏/关联、墓碑及已接收序号，执行 integrity_check 和 foreign_key_check。
4. 提交并关闭后原子切换存储入口，保存 migrationComplete 标记。中断时可从原备份重新建临时库，不能从一半导入结果续发回执。
5. 读取验证通过才恢复同步。云端继续 format 2，不同时修改数据库和云端协议；首次迁移不重传原图。
6. 双端分别完成真实数据及崩溃测试，再移除旧写路径。迁移失败时保留旧版本读取路径并停止新库写入；新库已经有新编辑后，禁止无提示回退到旧 JSON。需要显式从新库导出兼容 JSON 再回退。
7. JSON 保留为手动导出和周期备份格式，不再每次击键/提交都重写全库。备份保留策略独立于同步检查点和图片租约。

## 验收标准

以同一套 macOS/iOS Release 数据集测试 1k、10k、100k 条记录和大量原图引用，记录 p50/p95/p99，不使用 Debug 数字替代真机结果。

- 单条修改：SQL 行修改量、outbox 字节及前台准备时间基本不随全库大小增长；云端仍只传变更字段。统计真实 DB/WAL 写入字节和 checkpoint 峰值，不能只报 payload 大小。
- 空闲检查：无正文/数据库写事务，不重写回执或原图；只读取必要的云端元数据。
- 交互：下一帧延迟、每字延迟、拖动掉帧与迁移前同设备基线对比，测试大批次后台合并期间的输入。
- 故障：事务前/中/后退出、正文写失败、outbox 提交后发送前退出、回执前退出、目录更换、损坏 transport、丢失本机状态、缺失批次、图片回收后重引、导入中关闭/丢弃。
- 一致性：双端离线并发、第三台加入、重复/乱序批次、同 owner Board 合并、恢复历史、编号冲突、墓碑/别名重放均收敛，不能重发已丢失的旧正文。
- 迁移：先备份、验摘要、断点重启和失败恢复；原图字节摘要不变，手机存量数据不清空。

## 本轮验证记录

126 项相关 XCTest 通过（含 8 项同步恢复、3 项导入队列，以及快速记录/专注笔记的延迟附件测试）；窗口服务器监控未发现透明度大于 0 的测试窗口。iOS Release 模拟器构建通过。

iPhone 17 Pro / iOS 26.5 模拟器，修复前后均使用 Release、demoData、相同 PerfProbe 步骤及 3 轮动作。观察结果如下，仅为小样本，不推断统计显著性或真机表现：

| 测量 | 修复前 | 修复后 |
| --- | --- | --- |
| 逐字下一帧，13 个采样的平均 / 中位 | 3.9 / 3.8 ms | 6.5 / 2.9 ms |
| 逐字采样最慢 | 10.2 ms | 23.6 ms |
| 打开记一笔动作到下一帧，3 轮 | 16 / 28 / 24 ms | 5 / 40 / 33 ms |
| 关闭记一笔动作到下一帧，3 轮 | 37 / 25 / 20 ms | 64 / 36 / 23 ms |
| 冷启动输入卡片可见的 hitch | 251 ms | 278 ms |

这次修改解决导入和草稿生命周期，没有消除输入卡片首次打开的两百多毫秒卡顿。关闭和部分采样也有波动；后续应在真机及稳定数据集上增加重复次数，区分键盘/系统动画和草稿保存的耗时。没有增加每字保存或图片主线程解码。

本轮连接列表中的 iPhone 14 Pro Max 显示 unavailable，因此不将模拟器验证表述为真机验证或手机安装完成。

附件竞态 PerfProbe 使用真实 4000×3000 原图（1,552,696 字节），在真实导入前增加 2 秒延迟，确保跨过关闭界面时刻。验证输出 blockedEarlySave=true、lateResultPersisted=true。最终构建复测导入并尝试保存、关闭、重新打开到下一帧分别为 56 / 45 / 39 ms。延迟用于强制竞态，不计作导入性能；真实原图文件写入仍走后台路径。
