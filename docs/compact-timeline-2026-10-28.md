# 紧凑时间轴与剩余延迟

## 这轮布局

macOS 日记和任务 / 标签笔记共用时间轴：时刻移到节点左侧，正文列不再重复显示时刻。没有类型、任务、标签和日期说明的条目省掉整行元信息；元信息与正文间距从 5 pt 减到 3 pt，顶部从 6 pt 减到 4 pt，底部从 12 pt 减到 6 pt。无元信息时操作按钮悬浮显示，不影响正文宽高。日期节点、间隔提示、专注总结的线条随新列位置对齐。

曾尝试移除原生 Markdown 末尾的排版换行，全量回归发现会导致进入编辑时高度相差一行，并改变工作板披露内容的高度，因此已撤回。最终保留原有正文 / WebKit 编辑器排版协议，收紧外部布局。

iOS 不再逐条显示「专注笔记」标签；专注轮次的任务信息保留在开始和小结处，中间笔记省去重复的任务与标签。取消关联后，普通记录的任务、标签按原有规则显示，节点由当前 `focusMarker` 决定，INFO 使用灰色。

## iOS 取消关联检查

修改前先给当前源码加入 PerfProbe 操作步骤和渲染诊断，在同一个模拟器里运行「建立专注笔记 → 取消笔记关联 → 恢复笔记关联」三轮。三轮均观察到 NOTE → INFO → NOTE；INFO 的节点颜色函数返回 `Palette.muted`。因此本轮没有复现用户所述的不变色，不能把已有共享数据层行为说成这轮新修复。

共享数据层已经在取消关联时清空专注笔记的关联标记，并能兼容 `focusEvent == .note`、`taskID == nil` 的旧记录。iOS 行的等值比较也包含完整日志。需要在安装当前构建后判断手机上的旧构建或具体记录是否仍会复现。

新增 `PerfProbe` 步骤同时检查行 body 实际拿到的 marker、节点颜色及重复类型标签；交替修改关联可检测漏刷新。另记录修改后到下一次显示回调、以及行 body 更新后到显示回调的时间。回调不是像素已经呈现的证明。

## 剩余耗时与后续选择

上一轮修复导航绑定后，仍有绝大部分同步滚动工作落在 `layoutSubtreeIfNeeded`，不是推进滚动位置本身。这个阶段包含 SwiftUI 图更新、布局、原生文字控件测高和视图挂载，不能仅凭它的总耗时认定每次都是 Markdown 解析。

小页面在跨条目时也有布局峰值，说明只改变懒加载阈值不够。长页面的新行创建、不同宽度提案和高低差异很大的文本行会额外放大测量开销。正文测高已有按内容、样式和宽度的缓存；继续增加同类缓存前应确认未命中的原因。

建议按以下顺序继续，而不是直接替换整页渲染：

1. 给布局提案、测高命中、行创建次数分段计数，确认跨条目长帧的触发路径；保持悬浮、选择、编辑高度不变。
2. 把频繁更新的状态与静态正文分开，减少行内重复布局；检查是否能固定正文有效宽度，减少无用测量提案。
3. 若新行创建占主导，可试验少量邻近条目的预备与有上限的复用；解析等可并行工作提前做，AppKit 控件操作保留在主线程。上一轮扩大预排已经增加打开成本，不能无限增加预加载。
4. 如果 SwiftUI 列表布局依然是瓶颈，再做小范围原生 `NSCollectionView` / `NSScrollView` 复用原型，与现有正文和编辑器配合验证。它比整体 WebKit 文档迁移更容易逐步对照，但仍有选择、定位和可变行高的维护成本。

紧凑意味着同样速度每秒经过更多条目，页面总路程缩短不等于单帧加速。性能对照必须同时列出每帧耗时、超预算帧数和实际滚动距离。

## macOS 滚动实测

Release，隐藏窗口，显示回调驱动 4500 pt/s 滚动；刷新预算约 8.33 ms。记录滚动推进、强制布局和绘制的主线程同步工作，不能当作窗口服务器最终 FPS 或触控板输入到像素的延迟。每次采样单独运行，未并行编译或运行 iOS 探针。

紧凑后再次向上浏览的路程：数据副本从 4398 缩至 2700 pt；30 条日记从 6572 缩至 5522 pt；90 条日记从 20972 缩至 17822 pt；90 条笔记从 21420 缩至 18264 pt。因此相同速度经过的条目更多，不能把整段滚动耗时直接作为加速比例。

数据副本的 8.33 ms 超预算帧：修改前首次 28/78、再次 17/98；修改后第 1 次首次 15/40、再次 16/52；复测首次 1/70、再次 1/71。初次打开同步耗时为修改前约 572 ms、修改后约 472 / 183 ms。原生对照也有较大变化，说明系统运行状态影响明显，数据不足以证明真实数据页面稳定加速；第 1 次修改后还有一次 63.54 ms 的回调间隔，不能宣称消除了长帧。

复测中 90 条日记首次有 27/490 个超预算帧、再次 13/452；90 条笔记首次 33/462、再次 27/457。长页面的布局占同步工作约 92–96%，数据副本约 97%。30 条日记的布局成本下降，但长笔记仍未达到浏览器般稳定的跟手程度。下一步应先定位长页面的布局重算和测量提案，避免仅根据某一次较好读数宣称优化完成。

## 工作板 / 终端拖动与关闭回归

新增回归在修复前复现了两个独立问题：

1. 鼠标拖动事件已经排队时，按移动后的窗口原点再次将窗口内坐标转换到屏幕坐标，会把窗口已经移动的距离重复加进去。连续左右移动会形成位置反馈，表现为抽搐。改为使用事件携带的全局屏幕坐标，不再依赖当前窗口位置。
2. `fullSizeContentView` 的顶栏区域也可以放 SwiftUI 按钮。旧代码仅排除 `NSControl`，会把工作板的 SwiftUI X 当成原生标题栏并吃掉按下 / 松开事件。现在按命中的视图是否属于内容区区分，内容区继续收到点击；转发开始拖动的按下事件时暂时禁用系统移动，防止原生拖动和手动边界拖动争用。

原生窗口按钮和嵌套的 AppKit 控件保留完整事件，文本选择不启动窗口拖动。四边约束保留。测试覆盖排队事件、反复反向移动、拖动后的鼠标状态释放、普通事件修改窗口可移动性，以及实际工作板拖动后连续两次打开 / 点击 X 收起。全程使用隐藏窗口并监控窗口服务器。
