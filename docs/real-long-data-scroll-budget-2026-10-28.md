# 真实长数据：滚动预算与排版峰值

本轮接续 `344458e`，继续使用上一轮冻结的本机数据副本。原始数据不参与测试写入，正文、标题、标签、记录标识和图片不进入仓库。

## 定位与保留的改动

新建 `NSTextView` 尚未得到 SwiftUI 的实际宽度时，文本容器只有 1 pt。直接设置 `needsDisplay` 会同步填充 TextKit 排版，长正文因此先按 1 pt 宽度排一次，再按实际宽度重排。独立回归复现了这个过程：重绘请求前尚未排版的约 11K 字符，原先会全部进入错误宽度下的排版。

现在仅在容器宽度不超过 1 pt 时使用 AppKit 公开的 `setNeedsDisplay(_:avoidAdditionalLayout:)`，实际放置后的重绘维持原行为。不修改布局管理器的持久设置。回归同时检查最终完整排版、高度、换行和末尾链接区域。

第二个开销来自懒加载条目的反复创建，以及首次遍历时估算高度的修正。普通日志和独立日记窗口现在共用有上限的布局预算：最多 120 条、正文合计不超过 32,000 个 UTF-16 单元时一次排好。笔记页最多 80 条，正文同样限制为 32K；按章节显示时条数按展开部分计算，正文预算保守地计算整页。超过预算继续懒加载。右侧节奏条外层也不再订阅滚动位置，滑块保留订阅。

这不是全面改成 eager 布局。日记窗口原先只依据笔记页的 40 条阈值选择布局，84 条但正文并不长的日记也会持续挂载和卸载条目；现在两个日记入口使用相同的正文与条数预算。

## 未保留的尝试

- 持续启用、首次取得宽度后关闭，以及仅在失效请求中临时启用 `allowsNonContiguousLayout`：都能去掉长文大峰值，但笔记页同步布局 p95 回退，最终使用更窄的公开重绘接口。
- 将跨日期笔记展开成逐行数组：图片页首次峰值约 190 → 25 ms，但重复滚动 p95 升高，首次浏览轨迹也变化。
- 小批次加载：峰值分散，但回归发现尚未挂载条目的 UUID 跳转失效；没有保留该结构。
- 用 `Section` 表示日期分区：定位回归通过，性能没有改善，已撤回。

## 测量方法

Release 构建、1424 × 876 隐藏窗口、1.1 倍字号、4500 pt/s、约 120 Hz 显示回调；向上、返回、再次向上各一遍，每遍最多 8 秒。每个进程重新复制同一冻结数据，串行执行「最终版 A / 原版 / 最终版 B」，关闭布局诊断。四页分别为 49 条长日记、84 条日记、80 条且含 29 张图片的标签笔记、33 条任务笔记。

数字是移动帧中滚动、同步布局和绘制请求的合计耗时，不是实际屏幕呈现 FPS，也不是触控板到像素的输入延迟。最终版探针额外记录整遍主线程 CPU 与进程 CPU，包含帧回调之外的工作；每遍只在开始、结束计时。

两轮最终版的四页、三遍滚动，共 24 遍，移动帧同步工作超出 8.33 ms 预算的数量均为 0；错过刷新机会、主回调未完成导致的显示 tick 合并、超过 50 ms 的回调间隔也均为 0。这个结论仅对应上述隐藏窗口探针。

首次遍历路径因不再使用估算高度而变化：长日记原版累计位移 80,947 pt，最终版约 10,965 pt；84 条日记约 8,201 → 7,376 pt；图片笔记约 9,707 → 13,907 pt。首次 p95 不能当作相同轨迹的逐帧比较。再次遍历的距离基本一致，分别约 10,965、7,377、13,908、1,325 pt，最终版因布局取整相差不超过 1 pt。

## 打开时间与内存代价

同步打开时间不包含后续异步图片加载，也不等于完全可交互的总时间。

| 页面 | 原版打开 ms | 最终版 A / B 打开 ms |
| --- | ---: | ---: |
| 长日记 | 309 | 410 / 409 |
| 84 条日记 | 71 | 316 / 310 |
| 图片笔记 | 139 | 539 / 542 |
| 任务笔记 | 157 | 147 / 146 |

`/usr/bin/time -l` 的整进程峰值 RSS：原版约 455 MB，最终版约 508 / 515 MB；峰值 footprint 约 363 → 414 / 420 MB。数值使用十进制 MB，包含探针、四页与原生对照，不是单页长期占用。进程用户态 CPU 时间约 45.9 → 49.5 / 49.4 秒，没有整体降低；本轮主要把原先滚动时的挂载和排版移到有预算的打开阶段，而非声称总工作量消失。

最终版 A 再次遍历时，长日记主线程 CPU 约 495 ms、进程 CPU 3195 ms；图片页分别约 1274 / 4502 ms。进程 CPU 可以大于经过时间，因为它累计多个线程。仅看帧回调里的同步耗时会漏掉图层提交、绘制和其他事件循环工作。

## 当前边界

对于这份真实副本，常见长页面的重复滚动同步工作已经稳定在刷新预算内，继续增加 eager 预算没有针对这些页面的额外收益，只会扩大打开与内存成本。因此保留上述上限。

剩余明显延迟在首次打开：SwiftUI 创建行与原生文字视图、Markdown 和实际宽度下的排版、图层准备，图片尺寸与后台缩略图加载也仍有成本。超过预算的更大笔记本仍会经历冷行挂载及估算高度修正。要同时明显压低打开时间、内存和任意长文滚动成本，需要进一步分批构建、稳定高度虚拟化，或更换列表 / 文档承载结构；本轮没有做这种规模的改造，也没有证明当前架构的绝对极限。

## 复现与验证

沿用 [上一轮报告](real-long-data-layout-2026-10-28.md) 的副本准备与探针命令。最终版 JSON 新增 `mainThreadCPUMS`、`processCPUMS`，与 `statistics` 内的同步耗时分开阅读。正式比较关闭 `TIMELINE_LAYOUT_DIAGNOSTICS`；需要分段计数时再开启。

验证包含长正文失效与最终链接、不同宽度和字号的 Markdown、编辑器对齐、懒加载笔记跨日期定位、窗口与滚动回归。测试使用隐藏窗口，并由 AAA / ZZ 守门和窗口服务器监控共同检查。

最终代码的完整 Release 回归为 720 项、22 项按条件跳过、零失败；三轮交替性能探针每轮 6 项通过。额外开启诊断单独检查 84 条日记，再次遍历的正文创建、更新、尺寸询问、TextKit 测量计数均为 0，说明常见页面的挂载与排版没有继续发生在滚动阶段。该诊断轮单独运行且开启计数，不混入上面的性能对照。两段窗口服务器监控日志均未发现可见测试窗口。
