# iOS 保存延迟诊断与后续优化

## 真机验证的实际状态

iPhone 14 Pro Max / iOS 26.6.2 可以识别、读取设备状态和应用文件，开发者模式已启用。现有应用和扩展的缓存签名有效，沿用原 Bundle ID 的 Release 构建通过。

独立测试 Bundle ID 申请失败：Xcode 没有登录账户，无法生成新的 provisioning profile。因此增加 `-perfProbe YES -perfIsolated YES`，让同一签名下的性能运行使用 `Application Support/Timeline-Performance`、独立 defaults suite、独立草稿及同步配置；不启动系统搜索索引、不重排日常提醒、不结束日常实时活动，也不为这次运行安排后台刷新。没有这两个参数时仍使用正常数据。

实际安装未成功：CoreDevice 多次报告连接中断、socket closed、RSD 分配失败或安装超时；Xcode 指定真机目的地还报告 `Device is busy (Preparing HyL)`。重建 Mac 的用户级开发连接后可以重新读取设备详情，但安装仍超时。Instruments 设备列表同时将该手机列为 offline。失败发生在应用启动前，本轮没有有效的真机性能数字，也没有把签名构建成功当作安装成功。

安装尝试前后均回读手机原始 journal，SHA-256 相同。未将测速文字或样例日志写入日常库。真机开发连接恢复后，应使用下述隔离模式复测；重新运行普通安装后不带性能参数启动即可回到日常数据。

## 已定位的耗时

为异步保存增加可选计时，分别报告写队列排队、实际写入、完成回调等待，避免把整个 `await saveAndWait()` 当作磁盘耗时。

模拟器诊断样本中，队列等待约 9.3 ms、实际写入约 0.3 ms，但主线程回调等待约 81.4 ms；随后恢复保存任务还可能继续等待主线程。主要问题在交互与主线程调度，继续压缩 SQLite payload 不能解决这一段卡顿。

`sample` 调用栈记录到 `UIView.setUserInteractionEnabled` → `UITextView.resignFirstResponder` → SwiftUI 焦点查找及键盘重建。输入框的程序性 `setText` 也会触发选区和候选栏更新。Instruments 的 Time Profiler 启动没有产出有效 trace，不以该 trace 作证据；调用栈来自单独的进程采样。

## 本轮修改

- 新建日志使用单日期修改入口，只比较和追踪当天的任务/日志变化，保留原有撤销、删除保护和后台保存语义。
- 保存等待期间由 UITextView delegate 和 UITextInput 输入入口拒绝文字修改，仅禁用附件、标签等按钮；不再禁用持有焦点的整个输入区域，成功后按正常关闭路径收起键盘。回归探针发现直接 `insertText` 能绕过 delegate，因此控件本身也拦截插入、删除和组合输入。
- 保存成功后把草稿会话标记为已提交，保留退场视图中的原文字，避免先清空再关闭的排版和选区更新。下次打开创建新会话；旧会话的迟到回调不能恢复已提交草稿。保存等待中关闭又重开的同一会话，也会在确认后收起。
- 日记输入卡显示期间合并底页的数据通知，在退场后刷新一次；后台标签仍遵守原有可见性策略。操作宿主只把实时 store 交给操作闭包，不再订阅所有内容变化来重建整页环境。
- 增加“保存时继续输入”“保存后重新打开”“检查已保存草稿”探针，核对禁止修改、草稿清空以及保存后的日记投影包含新记录。

## 测速方法与限制

使用 iPhone 17 Pro / iOS 26.5 模拟器、Release、相同冻结的 SQLite 示例库和独立性能草稿。基线是 1b2c224 加相同隔离与分段计时探针，未含上述优化。两版每次启动都先实际投递相同 61 个字符，输入结束后再触发一次保存；每版独立启动 3 次，逐次恢复相同数据库。

没有把“程序设置一段文字后立刻保存”的动作混作正常打字后的保存：前者会把 UITextView 的程序性 setText 成本算进保存。诊断时单独测试过该路径，但不把它当作输入完成后的保存速度结论。

这里只比较动作至下一帧和持久化确认，不能把它们解释为所有像素均已完成呈现。底页刷新延后到退场之后，总页面更新时间及动画后段仍需单独观察；首次系统键盘初始化也未被消除。性能运行隔离了云端同步，不能由此推断合并期间的真机表现。

## 三次独立运行的结果

| 指标 | 基线 | 本轮修改 |
| --- | --- | --- |
| 保存动作至下一帧 | 87 / 85 / 96 ms | 69 / 70 / 22 ms |
| 下一帧中位数 | 87 ms | 69 ms |
| 保存动作至持久化确认 | 103.7 / 101.9 / 123.5 ms | 92.7 / 94.0 / 97.5 ms |
| 持久化确认中位数 | 103.7 ms | 94.0 ms |
| 各次打字平均延迟 | 11.2 / 11.4 / 11.0 ms | 10.9 / 11.0 / 11.3 ms |

所有运行均收到完整 61 个字符。最终版本首帧中位数减少约 21%，但三次样本很少；打字延迟未显示稳定改善。中间版本也曾测出 72 / 21 / 22 ms，最终重新构建后没有稳定复现其 22 ms 中位数，因此采用表中最终版本数据。当前实际 SQLite 写入仅约 0.13–0.19 ms，主线程回调仍等待约 75–77 ms。不能据此宣称全部卡顿消除，也不能外推到大库或真机。

日记底页的合并刷新在输入卡关闭后延迟 300 ms 执行，避免和退场动画争用；这不是减少了全部页面处理量。下一步应在真机连接恢复后，用更大日志库和真实附件复测键盘、日记排版与同步合并的竞争，再决定是否需要进一步分拆日记投影。

## 回归验证

- 相关自动测试共 332 项，0 失败；其中 1 项本地性能基准按原有条件跳过。包含 TimelineCore、FocusNoteDraft、QuickCaptureAssociation、LogImageTools、NotesNavigation 和 ZZNoVisibleWindows。窗口监测未记录到可见测试窗口。
- 最终 iOS Release 模拟器构建及沿用现有签名的真机构建通过。
- 实际输入后保存时尝试继续输入：`inputBlocked=true`；重新打开后 `cleared=true pending=false`，日记投影包含刚保存的 ID。
- 4000×3000、约 1.55 MB 原图导入期间立即保存被阻止；关闭后导入结果仍写回草稿，重开保存成功。重新读取 SQLite 确认仅新增一条日志，原图存在，`PRAGMA integrity_check` 通过。
- macOS 正常退出后执行 `bash scripts/install.sh`，完成备份、安装与重新打开。安装前后 SQLite 实体数量保持 52 个任务、758 条日志、25 天和 12 个工作板，完整性检查通过。真机安装及真机性能验证仍未完成。
